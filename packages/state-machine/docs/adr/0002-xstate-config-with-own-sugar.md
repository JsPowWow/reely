# XState's config vocabulary, with our own sugar

A machine is written as a config that reads like a schema, and XState already taught that schema to many readers, so where XState has a key we use it: `initial`, `context`, `states`, `on` (on a state, and on the machine for any-state transitions), `entry` and `exit` on a state, `{ target, actions }` on a transition, and one term, Action, for all three kinds of function; each takes one function or an array. Where XState has nothing that fits, we keep our own sugar: a target given as a plain string, a target selector (a function returning the target, or `undefined` to refuse), `send(type, data)` with the data required or forbidden by the event's type, a result from `send` (`done`, `refused`, `failed`, `queued`), the sync and async factories, and the `matchAction` / `runActionEffect` pair (data first and data last, as `pipe` and `flow`).

An action gets `{ step, context, event: { type, data }, from, to, machine }`. Its `machine` is the machine's inner face: while a transition runs, `send` from it answers `queued` and runs the transition right after the current one. `send` on the machine itself answers the same while the machine calls an action or a listener (the part before its first `await`), so both machines behave alike, and an async action that awaits such a `send` does not wait for the transition it runs inside. One case stays out of reach: an async action that awaits `send` of the machine itself after another `await` waits for itself forever, because nothing in JavaScript tells that call apart from one made outside; the README says to use `change.machine`.

The async machine awaits the target selector and every action, so `entry` starts only after `exit` has finished; its selector returns a promise (an `async` function), because TypeScript widens the state an async function returns where a plain value may come back too. The sync machine fails a transition whose selector or action returns a promise, rather than running on before it settles.
